## 1. Зачем

Инструменты есть, слой сломан: модель видит то `ToolsCore`, то полный `Tools()` (и не влезает в 32K), руки браузера всплывают в основном по `/browser`, локальная LLM тыкает тулы вразброс.

Нужен ассистент: любой запрос текстом или голосом → сам понял → сам выбрал руки → сделал → ответил человеку. Telegram и Web — **одно ядро** (`AGENTS.md`).

## 3. Мозг и железо

- Модель: `models/brain/Qwen3.6-35B-A3B/Qwen3.6-35B-A3B-UD-IQ4_XS.gguf` + `mmproj-BF16.gguf`
- GPU: обе 3060, `LLAMA_TENSOR_SPLIT=0.35,0.65`, `LLAMA_DEVICE` пустой
- Reasoning в цикле рук: **off**. План — JSON без длинного CoT. Если thinking тормозит — тоже off
- Второй мозг не поднимаем

### 3.1. Контекст

Старт **32K**. Цель 64K — гипотеза. План Б: KV `q4_0` → `--no-mmproj-offload` → 48K → стоп на 32K.

`--parallel 2` **не запасной план при 32K**: llama-server делит `n_ctx` между слотами (32K / 2 = 16K на слот). Писать «`--parallel 2`» можно только если 64K реально встало — тогда это 2×32K. Пока 64K не доказан — вычёркиваем.

### 3.2. KV-кэш промпта

Короткий промпт диспетчера удешевляет **вызов диспетчера**, но префикс-кэш **исполнителя** при переключении слота/префикса всё равно вытесняется.

Реальная цена v1 = **один раз на задачу** переобработать system-промпт исполнителя (~1–2K токенов). Внутри цикла рук вызовы идут подряд, кэш держится. Это скорее терпимо.

Мерить в логах именно `prompt_ms` **первого** хода исполнителя после диспетчера, не длину диспетчерского промпта. Промпт диспетчера всё равно держать коротким (история 2–3×300 + few-shot + таблица паков).

`--cache-reuse N` (принимает **число** токенов, не флаг) — опция, если замеры плохие. `--parallel 2` — только после §3.1.

## 4. Слои

```
пользователь (текст | голос | слэш | картинка)
        ↓
   [вход]
     /stop и /hands  →  ДО очереди (поллинг / HTTP), activeTask.Cancel
     голос → STT → текст
     картинка → vision БЕЗ tools → текстовое описание (+ подпись)
     слэш → подсказка пака, не обход диспетчера
        ↓
   [Task] taskID, Actor, ctx с TaskTimeout 10 мин  (§4.0)
        ↓
   СЛОЙ 1. Диспетчер (тулов нет)
        вход: запрос + паки + режим + часы
              + 2–3 хода (~300 симв.) + agentURLBag + сводка памяти
              + 3–4 few-shot web vs trade
        выход: JSON {packs[], plan[], confirm, summary}
               confirm — UX, НЕ гейт
        ↓
   СЛОЙ 2. Сбор рук
        схемы паков + request_pack (кап 3 и бюджет схем)
        дедуп по имени
        ↓
   СЛОЙ 3. Исполнение (thinking OFF, ctx отменяем ДО дочерних процессов)
        tool_call → guardToolCall(actor, …) → Decision
          allow      → Dispatch(ctx, …) → ToolResult{Text, Status, Artifacts}
                       в модель уходит только Status + Text
          deny       → в модель «запрещено»; +1 к fingerprint и tool
          hard_block → выход из задачи, без счётчика
          ask        → статус, отпустить мьютекс, pending:
                       метаданные на диск + сжатые шаги в RAM,
                       остальным tool_calls этого хода — синтетический «отложено»
        web-нуджи: shouldForceRead / looksLikeNewsOrResearch
        ↓
   СЛОЙ 4. Ответ
        summary диспетчера — первая строка, plan — лента статусов
        в память — финальный текст, не JSON тулов
        прерванные (/stop, timeout, отказ по pending) в память НЕ пишем
        строка в tasks.jsonl
```

Агент глобально однопоточный (`browserTaskMu`). Параллельный канал: минимум «занят, в очереди». Web = один `webChatID`.

**Диспетчер не граница безопасности.** `chat` + `request_pack("console")` технически возможно. Режут руки `guardToolCall` и allowlist канала, не роутинг. Через полгода не утверждать обратное.

## 4.0. Задача как объект

Без этого состояние размазано по трём мапам с ключом `chatID` (cancel, pending, артефакты), а `chatID` — не задача.

```go
type Task struct {
    ID        string    // task-20260812-000123
    ChatID    int64
    Channel   string    // telegram | web
    Actor     Actor     // {mode, channel, chatID, isOwner}

    Input     string
    Packs     []string
    Plan      []string

    Status    TaskStatus
    Step      int

    Steps     []CompactResult   // сжатые результаты для возобновления (§6.3 п. 4)
    Artifacts []string          // свои, не общий буфер сессии
    FailCount map[string]int    // ключ — fingerprint, см. §4.2

    Pending   *Pending
    Deadline  time.Time         // §4.2, TaskTimeout
    Cancel    context.CancelFunc
}
```

`TaskStatus`: `running | waiting_confirm | done | cancelled | failed | expired | lost`.

Формальную FSM с таблицей переходов не рисуем — состояний шесть, переходы очевидны из §6.3. Достаточно enum'а и того, что статус пишется в `tasks.jsonl`.

Адресация — `chatID → activeTask`, дальше всё через `Task`:

```
chatID → activeTask(*Task) → cancel | pending | artifacts | steps
```

Инвариант: **одна активная задача на чат** (агент и так однопоточный по `browserTaskMu`). Вторая — «занят, в очереди». Это делает гонки из внешнего ревью невозможными по конструкции, а не по аккуратности.

`taskID` идёт **во все логи** (`hands.jsonl`, `tasks.jsonl`) — по нему восстанавливается вся цепочка: вход → паки → тулы → pending → финал.

## 4.1. Диспетчер

```json
{
  "packs": ["web", "files"],
  "plan": ["найти 3 статьи", "прочитать", "сохранить выжимку в md"],
  "confirm": true,
  "summary": "найду статьи и сохраню"
}
```

**Куда идёт каждое поле** (иначе `plan` и `summary` реализуют и не подключат — мёртвые поля):

| Поле | Потребитель |
|---|---|
| `packs[]` | сборка схем (СЛОЙ 2), валидация по белому списку имён |
| `plan[]` | в system-промпт исполнителя блоком «намеченные шаги» **и** в UI как лента статусов |
| `confirm` | сразу человеку: «возможно, попрошу подтверждение». Не гейт |
| `summary` | первая строка ответа («найду статьи и сохраню») |

Правила в промпте:

- болтовня / «помнишь, о чём просил» → `chat`
- новости, факты, «что сейчас», «что по BTC» → `web`
- вкладка / клик / форма → `browser.read` / `browser.act`
- shell → `console`
- пути, сохранить → `files`
- скачать ролик → `media`
- явный разбор тикера / график / сайзинг / журнал сделки → `trade`
- логи бота, IOC, аудит файла → `secops`

**Few-shot в промпт диспетчера (обязательно, это основной домен):**

| Запрос | packs | Почему |
|---|---|---|
| «Что сегодня по BTC?» | `web` | новости/факты |
| «разбери ETH» / «разбери эфир» | `trade` | явный разбор |
| «что там с эфиром?» | `web` | серая фраза = новости, не стакан |
| «залогируй лонг BTC от 108к» | `trade` | журнал |

История 2–3 хода + URL-bag обязательны (follow-up «сохрани это» / «прочитай подробнее»).

Память: сводка → диспетчер, recall → исполнитель, в store — финальный ответ.

**Прерванные задачи в память не пишем.** `/stop`, отказ по pending, таймаут подтверждения — `rememberExchange` не зовём. Иначе в recall осядут обрывки («хотел удалить папку…»), и они всплывут в следующем диалоге как факт.

Fallback, если JSON дважды сломан:

- голый video URL → `media`
- **всё сообщение = тикер ± одно слово** → `trade`
- иначе **смещение в `web`**, не в `chat`, если запрос хоть как-то про факты/рынок/«что там». `chat` только на явное приветствие/теорию без фактов

## 4.2. Исполнение

- `maxAgentSteps`: 12 — **жёсткий потолок в коде**, не инструкция в промпте. Адаптивный бюджет шагов по типу задачи — не в v1.
- Несколько `tool_calls` в ходе: подряд. Если один ушёл в `ask` — см. §6.3 п. 5, остальные **обязаны** получить `tool`-ответ.
- Бюджет контекста: сжимать старые tool-результаты (`compactToolMessages`). Не подменять паки на `ToolsCore`.
- Цикл крутится под `context.Context` задачи: его рвут `/stop` **и** `TaskTimeout`.

### Счётчик провалов — по отпечатку, не по имени

`failCount[name]` ловит зацикливание, но `delete_path(A) → deny` и `delete_path(B) → deny` — это **разные** намерения, и глушить второе из-за первого неправильно.

Два счётчика:

| Ключ | Порог | Смысл |
|---|---|---|
| `fingerprint = tool + нормализованные args` | 2 | одно и то же действие повторяется — вернуть модели «ты это уже пробовал, результат тот же» |
| `tool` | 4 | тул в принципе не работает / запрещён — выйти из цикла честно |

`deny` считается в оба. `hard_block` — сразу выход, без счётчика.

### `ToolResult` — статус, а не строка «ошибка»

Сейчас `Dispatch` возвращает `(string, error)`, а ошибка склеивается в текст `«Ошибка инструмента X: …»` (`agent.go` ~693). Модель не отличает «упало» от «запрещено» и от «убито по таймауту» — и повторяет вызов.

```go
type ToolResult struct {
    Text      string        // ЕДИНСТВЕННОЕ, что уходит в контекст модели
    Status    ResultStatus  // ok | failed | denied | blocked | timeout | cancelled | deferred
    Artifacts []string      // человеку, не в контекст
    Err       error         // в логи, не в контекст
}
```

В `tool`-сообщение модели уходит `Status` строкой + `Text`. Картинки, файлы и метаданные — мимо контекста (§7: «картинка + tool-schemas» в llama-server ломается по-разному; `capture_screenshot` и так возвращает путь).

**Отдельно про `timeout`.** Текст обязан быть таким, чтобы модель не переспрашивала вслепую:

> `timeout: процесс убит по таймауту. Состояние неизвестно — команда могла успеть выполниться. НЕ повторяй тот же вызов, проверь результат.`

Полноценный registry идемпотентности (`executionID → status`) в v1 **не делаем**: решение о повторе принимает модель, а не рантайм, и реестр этого не меняет. Единственное место, где нужен настоящий ключ дедупликации — `journal_add` (двойная запись сделки): туда добавить `client_id = taskID + tool_call_id` и отбрасывать дубль на уровне `journal/`.

### Потолок задачи

`TaskTimeout` = **10 минут** на всю задачу, от диспетчера до финала. Ожидание pending в него **не** входит (у него свои 5 минут).

Иерархия обязательна: `task ctx` → `tool ctx` → `process ctx`. Таймаут тула **урезается** до остатка задачи, а не наоборот. Сейчас `run_command` может попросить 600 с — при `TaskTimeout` он получит `min(600, остаток)`.

По истечении — `Status = expired`, человеку «задача шла 10 минут, остановил».

### Анти-галлюцинация (не потерять при рефакторинге)

Сейчас это единственное, что мешает ответить новостями из головы после одного `web_search`: `shouldForceRead`, `looksLikeNewsOrResearch`, нудж «ты ещё не вызвал read_url» (`agent.go` ~215, 513–561).

**Сохранить.** Включать, когда в активных паках есть `web` (включая после `request_pack("web")`). Логика остаётся в Go, не в промпте.

Приёмка: после `web_search` модель **не** отдаёт финал без `read_url` на новостном запросе.

### `/stop` — до очереди, иначе не дойдёт

Telegram: `enqueueMessage` → `chatWorker` → `safeHandleMessage` (`main.go` ~225–273) — строго последовательно в чате, `chatQueueCap=8`. Пока крутится задача, `/stop` лежит в очереди и исполнится **после** неё. Ручка из ТЗ в текущей архитектуре мертва.

Вписать в код:

- `/stop` и `/hands` разбираются **в цикле поллинга, до `enqueueMessage`**
- `chatID → activeTask` (§4.0), отмена берётся из `Task.Cancel` — отдельной мапы `chatID → cancel` не заводим
- `/stop` зовёт `cancel()`, ставит `Status = cancelled`, снимает pending, отвечает «остановлено»
- Web: `/api/stop` то же на `webChatID`
- «да/нет» на pending в очередь можно: воркер уже свободен
- **Пред-очередной путь всё равно проверяет права:** `allow[chatID]` / `TELEGRAM_ID` до `cancel()`. Он идёт мимо обычного обработчика — именно поэтому легко забыть и получить «любой чат гасит задачи хозяина»
- `activeTask` **снимать по завершении** (`defer`), иначе поздний `/stop` отменит уже другую задачу. `/stop` без активной задачи → «нечего останавливать»

`/stop` идёт вместе с guard (§12 п. 3), а не после pending — нужен уже на нынешнем цикле.

### Отмена должна доходить до дочерних процессов

Отменяемого ctx у цикла **недостаточно**. Сейчас каждый долгий дочерний процесс делает себе контекст от `context.Background()` и про отмену задачи ничего не знает:

| Место | Что запускает | Потолок |
|---|---|---|
| `browser/terminal.go` ~38 | `powershell` / `bash` | до 600 с |
| `browser/reach.go` ~340 (`runQuick`) | `agent-reach`, `yt-dlp` (субтитры) | 180 с |
| `browser/video.go` ~148 | `yt-dlp` (скачивание) | `videoDownloadTimeout` |

Плюс `Dispatch` вообще не принимает контекст (`browser/tools.go` ~154).

Без правки `/stop` останавливает агента **между шагами**: запущенный powershell доигрывает свои две минуты. При `full` и 600-секундном потолке это неприемлемо.

**Вписано в работу (§12 п. 0, до всего остального):** протащить контекст —

```
executeToolCall(ctx, …) → Dispatch(ctx, name, args) → RunCommand(ctx, …)
                                                    → runQuick(ctx, …)
                                                    → DownloadVideo(ctx, …)
```

Внутри — `context.WithTimeout(ctx, …)` вместо `context.Background()`: и таймаут тула, и отмена задачи работают вместе. Сигнатуры публичные, поправить вызовы в `browser_test.go` / `terminal_test.go` / `media_test.go`.

Если решим НЕ делать в v1 — переписать приёмку №16 на «останавливается после текущего шага», а не врать «сразу».

### 4.3. `request_pack`

Always-on. Кап **по двум осям сразу** — счётчика мало, три маленьких пака ≠ три больших:

1. не более **3 эскалаций** на задачу;
2. и суммарные схемы после подмешивания **не превышают порог §5** (12K символов до ×3).

Что первое упёрлось — то и остановило. Отказ: «лимит паков, закончи с тем что есть».

`request_pack` **не может запросить сам себя** и не может запросить уже активный пак (иначе модель тратит эскалации впустую). Неизвестное имя → ошибка модели, не `Dispatch`.

Лог в `hands.jsonl` (`decision=auto`, `rule=pack_escalation`).

|---|---|---|
| `analyze_ticker`, `size_position`, `journal_*` | allow | allow |
| `place_order`, `cancel_order` | ask | **ask** (рубильник рук на деньги не распространяется) |
| `transfer`, `withdraw` | `hard_block` | `hard_block` |

Одна строка в ТЗ сегодня — против «а почему бот слил депозит» потом. Полноценную capability-модель (`tool → capability → policy`) при этом **не строим**: пока паки и есть группировка прав, второй слой маппинга удвоит конфиг без нового поведения.

**`browser.act` — проверка вкладки перед действием.** Между `get_text` и `click_element` страница могла смениться: редирект, попап, новая вкладка, ушедший фокус. Модель скажет «жми кнопку», а агент уже не там.

v1-минимум (дёшево): перед любым действием из `browser.act` сверить URL активной вкладки с тем, что был на последнем чтении. Разошлось → не кликать, вернуть модели `failed: страница сменилась (было X, стало Y), перечитай`. Полноценную адресацию `pageID` / `frameID` / expected-origin в сигнатурах тулов — не в v1, это переделка `browser/`.

Не в v1: Playwright, почта, Docker, клик по скрину, второй LLM, любые ордера, `pageID` в сигнатурах.

`TestPackSchemaBudget` — **с конкретным числом**, иначе порог подгонят под зелёный.

Опора на то, что уже в коде (`agent.go`): `agentSoftBudgetChars = 48_000` на весь промпт цикла и множитель **×3** на схемы в `estimateAgentChars` (jinja-шаблон раздувает их примерно так).

Порог: `json.Marshal` worst-case объединения (`web` + `browser.read` + `browser.act` + `console` + `files` + `media` + `trade` + `secops` + `request_pack`) **≤ 12 000 символов до множителя**. То есть ≤ 36K после ×3 — остаётся ~12K на system-промпт, историю и tool-результаты внутри 48K.

Пока тест красный — резать **описания** схем, а не надеяться на `shrinkAgentMsgs` в рантайме.

## 6. Безопасность

### 6.0. Ворота

```
executeToolCall(ctx, …) → guardToolCall(actor, name, args) → Decision
                              allow      → Dispatch(ctx, …)
                              ask        → pending (§6.3)
                              deny       → в модель, +failCount
                              hard_block → выход из задачи, без счётчика
```

`actor`: `{mode, channel, chatID, isOwner}`. Без него guard не проверит «полные руки только allowlist / localhost» и не адресует ask в нужный канал.

Решение — **структура, а не одно слово**. Это стоит ноль, а при отладке отвечает на «почему он спросил?» без чтения кода:

```go
type Decision struct {
    Action Action   // allow | ask | deny | hard_block
    Risk   string   // low | medium | high
    Rule   string   // protected_path | outside_allowlist | unparseable_cmd | nuclear | pack_escalation
    Reason string   // «перезапись settings.ini»
}
```

**`deny` и `hard_block` — разные вещи.** `deny` — «в этом режиме нельзя, в `full` было бы можно». `hard_block` — «нельзя никогда, ни в каком режиме» (§6.2, плюс `withdraw` из §5). Разные слова в коде и в журнале, иначе через полгода их сольют.

Отдельный «Security Policy Engine» с семиступенчатым конвейером не заводим: это одна функция с пятью проверками в однопользовательском инструменте. Важна **структура решения**, а не число пакетов вокруг неё.

`confirm` плана — не гейт.

### 6.1. Allowlist путей + «не доказал → ask»

Allowlist записи/удаления: проект, Desktop, `engine-go/runtime/`, плюс `AGENT_HANDS_ROOTS`. Чтение — `allow`.

**Правило по умолчанию:** не смог **доказать**, что цель внутри allowlist → `ask` в `safe`. Не «если разобрали путь и он вне — спросить», а «если не доказали, что внутри — спросить».

Триггер разбора цели — любой **мутирующий глагол** (после нормализации):  
`Remove-Item`, `del`, `rm`, `Move-Item`, `Set-Content`, `Out-File`, `>/>>`, `New-Item`, `Copy-Item`, `reg add`, `sc`, `schtasks`, `net user`, `icacls`, плюс `delete_path` / `write_file` / `mkdir`.

Неразбираемые формы (`-EncodedCommand`, `iex`, `Invoke-Expression`, `FromBase64String`, `curl … | iex`, обфускация) в `safe` → `ask` («не могу классифицировать»).

Нормализация: снять backtick и обёртки кавычек, схлопнуть пробелы, lower.

**Защищённые пути — на все мутирующие тулы**, не только `write_file`: `settings.ini`, `Start.cmd` / `Stop.cmd` / `Menu.cmd` / `build.cmd`, `.git/`, автозагрузка.  
Каталог проекта в allowlist **не** делает `Remove-Item .git -Recurse` или `run_command` по `settings.ini` автоматически `allow`. В `safe` это `ask` (`rule=protected_path`). В `full` — `allow` (кроме `hard_block`).

`agent_reach` — опасное (`ask` в `safe`).

`write_file`: новый файл внутри allowlist и не protected → `allow`. Перезапись существующего вне рабочих / любой protected → `ask`.

### 6.2. Режим `full`

`ask` → `allow`. `deny` → `allow`. **`hard_block` остаётся `hard_block`** — рубильник на него не действует.

Список `hard_block` (после нормализации): `format`, `diskpart`, `bcdedit`, переразметка, снос корня диска (`C:\`, `/`), `shutdown /s` / `reboot`, плюс `transfer` / `withdraw` из §5.

Это защита от **ошибки модели**, не песочница. В `full` через `-EncodedCommand` можно почти всё — так задумано рубильником. Не ссылаться на `hard_block` как на sandbox.

### 6.3. Подтверждение без дедлока и без переисполнения

Мьютекс на время «жди да» держать нельзя.

Поток:

1. Статус «жду подтверждения».
2. Отпустить `browserTaskMu`.
3. **На диск** (runtime-store) — только метаданные pending: `{id, chatID, channel, tool, args, deadline}`.
4. **В памяти процесса** — сжатые результаты уже сделанных шагов (тот же смысл, что `compactToolMessages` в `agent.go` ~488): маленький JSON, не живой `[]msg`. Плюс исходный запрос, выбранные паки, что именно ждём.
5. **Остальным `tool_calls` этого же хода — синтетический `tool`-ответ** «отложено, жду подтверждения». Протокол требует ответ на **каждый** `tool_call_id`; если вызов №2 ушёл в pending, а №3 остался без `tool`-сообщения, следующий запрос к llama-server прилетит **400**. На возобновлении отложенные либо переигрываются, либо модель планирует заново — но дырки в истории быть не должно.
6. **Артефакты забрать в момент паузы**, не в финале. `TakeArtifacts` работает на общем буфере сессии (`agent.go` ~290): пока висит pending, соседняя задача заберёт чужие файлы. С `Task.Artifacts` (§4.0) это решается по конструкции — сливать буфер сессии в задачу после **каждого** шага, а не в конце.
7. **Один pending на чат** — следствие инварианта «одна активная задача на чат» (§4.0). Новая задача аннулирует старый pending с уведомлением («отменил ожидание подтверждения на удаление D:\tmp\old»). `pending.taskID` адресует «да» однозначно.
8. «Да» → **продолжить с этих сжатых результатов**, выполнить **только** подтверждённый тул, затем обычный цикл. Не гонять заново поиск / `read_url` / уже записанный файл / уже скачанное видео. `run_command` не идемпотентен.
9. «Нет» / таймаут 5 мин → отказ, pending стереть.
10. Рестарт мозга / процесса: RAM пустая → pending на диске помечаем протухшим, человеку честно: «задача потерялась, повтори». Не доигрывать вслепую.
11. Одно «да» = одна операция.

### 6.4. Рубильник

Только runtime-store (`runtime/hands_mode.json`). Не `settings.ini` (`loadConfig` один раз при старте).

Default `safe`. Хозяин: `TELEGRAM_ID` / localhost. Web-тумблер + Telegram `/hands` (до очереди). Один файл на оба канала.

### 6.5. Два журнала

**`runtime/hands.jsonl`** — решение guard на каждый tool-call:

```
ts, taskID, channel, chatID, mode, tool, args_cap,
decision, risk, rule, reason, status, exit
```

`decision`: `auto | asked | approved | denied | blocked`.  
`risk` / `rule` / `reason` — прямо из `Decision` (§6.0). Без `rule` журнал отвечает «спросил», но не «почему спросил».

**`runtime/tasks.jsonl`** — одна строка на **задачу**, пишется в финале:

```
ts, taskID, channel, chatID, input_cap, packs, escalations,
steps, tools[], status, dispatcher_ms, total_ms, artifacts
```

Это то, что реально отвечает на «почему он вчера сделал X»: по `taskID` из `hands.jsonl` поднимается вся задача целиком. Полноценную телеметрию (TTFT, tokens/sec, счётчики компактизаций) в v1 не заводим — на одного пользователя это стенд ради стенда; `dispatcher_ms` + `total_ms` + `prompt_ms` из §3.2 закрывают вопрос «где тормозит».

Ротация обоих: файл ≥ **5 МБ** → `*.jsonl.1` (одна предыдущая копия), новый с нуля. `/logs` без аргумента читает текущие.

## 10. Приёмка

1. «Что сегодня по BTC?» → **web**, не trade. После `web_search` нет финала без `read_url`. Ссылки, без выдумки.
2. «что там с эфиром?» → **web** (серая фраза = новости).
3. «разбери эфир» и `/analyze ETH` → **trade**.
4. Голосом «скачай это видео» + URL → media.
5. Chrome + сохрани заголовок на рабочий стол → browser + files (`request_pack`, если надо).
6. «Заполни поле…» → `browser.act`.
7. «Удали D:\tmp\old» в `safe` → pending, мьютекс свободен, `/hands` живой. «Да» исполняет **только delete**, уже сделанный поиск не повторяется. Таймаут 5 мин → отказ. `full` → сразу + `hands.jsonl`.
8. Тумблер Web ↔ Telegram.
9. «Привет» → chat. (Может вызвать `request_pack`; guard всё равно стоит.)
10. Ядерная команда в `full` → `blocked`.
11. Follow-up «а теперь сохрани это в файл» → files.
12. Эскалация `request_pack("files")`. Четвёртая эскалация — отказ.
13. Второй канал → «занят».
14. `-EncodedCommand` в `safe` → ask.
15. `Remove-Item .git -Recurse` из проекта в `safe` → ask (protected path на любом мутирующем туле).
16. `/stop` во время `run_command` со `Start-Sleep 120` → **дочерний powershell убит**, ответ «остановлено» приходит в течение секунды. Не «после конца шага».
17. «Помнишь, о чём просил вчера?» → chat + память.
18. Перезапись `settings.ini` через `write_file` в `safe` → ask.
19. `Get-Date`, `git status`, `go test ./...`, запись нового файла в `runtime/` в `safe` → **auto, без ask**.
20. Рестарт мозга при живом pending → «задача потерялась, повтори».
21. Ход с тремя `tool_calls`, где второй уходит в `ask` → третий получает «отложено», **следующий вызов модели не падает с 400**.
22. Новая задача в чате при висящем pending → старый аннулирован с уведомлением; артефакты новой задачи не содержат файлов старой.
23. Модель дважды зовёт запрещённый тул → выход с «не дам это сделать», а не 12 шагов по кругу.
24. `/stop` из чата **вне allowlist** → игнор, чужая задача продолжается.
25. `plan[]` виден в UI лентой, `summary` — первой строкой ответа. Поля не мёртвые.
26. Прерванная `/stop` задача **не появляется** в recall следующего диалога.
27. Задача, упёршаяся в 10 минут → `expired`, человеку «шла 10 минут, остановил». `run_command` с `timeout_sec=600` за 9-й минуте задачи получает остаток, а не 600 с.
28. `run_command` убит по таймауту → в `tool` уходит `timeout: … состояние неизвестно, НЕ повторяй`, и модель **не** зовёт ту же команду снова.
29. `delete_path(A)` → deny, затем `delete_path(B)` → deny: работа продолжается (разные отпечатки). Тот же `delete_path(A)` дважды → «ты это уже пробовал».
30. `request_pack` четвёртый раз → отказ. `request_pack` при исчерпанном бюджете схем → отказ **раньше** счётчика.
31. `request_pack("request_pack")` и запрос уже активного пака → ошибка модели, эскалация не тратится.
32. `get_text` на вкладке A → редирект на B → `click_element` → `failed: страница сменилась`, клика нет.
33. `/chart` со скрина: число в разборе совпадает с Binance, а не с тем, что «прочитал» vision.
34. По `taskID` из `hands.jsonl` в `tasks.jsonl` находится вся задача: вход, паки, шаги, тулы, исход.

## 12. Порядок реализации

0. **Протаскивание `ctx`** — чисто механический рефактор, делать **первым**, пока код не оброс новым: `executeToolCall(ctx, …)` → `Dispatch(ctx, …)` → `RunCommand` / `runQuick` / `DownloadVideo`, внутри `context.WithTimeout(ctx, …)` вместо `context.Background()`. Поправить вызовы в тестах. Без этого `/stop` и `TaskTimeout` — половинчатые.
1. **Каркас задачи (§4.0):** `Task` + `taskID` + `TaskStatus` + `chatID → activeTask` вместо трёх мап. Сюда же `TaskTimeout` 10 мин (иерархия task → tool → process), `Task.Artifacts` вместо общего буфера сессии, `tasks.jsonl`.  
   Делать до guard: `actor` и `taskID` берутся отсюда, иначе их придётся вкручивать задним числом.
2. **`ToolResult{Text, Status, Artifacts, Err}`** вместо `(string, error)`. В контекст модели — только `Status` + `Text`. Текст `timeout` — по формулировке из §4.2.
3. **`guardToolCall(actor, …)` → `Decision{Action, Risk, Rule, Reason}` + `hands.jsonl` (+ ротация) + allowlist + protected paths на все мутации + неразбираемый PS → ask + `hard_block` отдельно от `deny` + негативные тесты.**  
   Зеркало: `Get-Date` / `git status` / `go test` / запись в `runtime/` = auto.  
   Счётчики: `fingerprint` (порог 2) и `tool` (порог 4); `deny` в оба, `hard_block` — сразу выход.  
   **`/stop` в поллинге до очереди + `cancel` из `Task` (+ проверка прав, + чистка).**
4. Рубильник runtime-store + `/hands` (тоже до очереди) + тумблер Web. Все новые `/api/*` через `sameOriginGuard`.
5. Неблокирующий pending: метаданные на диск, сжатые шаги в RAM, продолжение не с нуля, синтетические «отложено» на остальные `tool_calls`, `pending.taskID`, артефакты сливаются в `Task` после каждого шага, протухание при рестарте.
6. Нарезка паков + дедуп + `TestPackSchemaBudget` (порог 12K символов до ×3) + сплит browser.
7. `request_pack`: кап 3 **и** остаток бюджета схем; без рекурсии и повторов активного пака.
8. Диспетчер: история, URL-bag, память, few-shot web↔trade, fallback со смещением в `web`. **`plan` → в промпт исполнителя и в ленту UI, `summary` → первая строка ответа.**
9. **Перенос, не удаление**, нуджей `shouldForceRead` / `looksLikeNewsOrResearch` на пак `web`.
10. Схемы `trade` / `secops` (+ `client_id` для `journal_add`). Проверка смены вкладки перед `browser.act`. Чат и голос через диспетчер. Vision без tools; числа `/chart` — из Binance.
11. Память: в store только финал, прерванные задачи не пишем. Статусы «занят». Приёмка §10.
12. Только `engine-go/build.cmd`, затем `go test ./...`.

## 14. Отклонённые предложения (чтобы не возвращаться)

Внешнее ревью предложило 13 «обязательных» пунктов. Двенадцать полезных идей взяты (см. §13). Остальное отклонено — здесь причины, чтобы следующий круг ревью не начинался с нуля.

| Предложение | Почему не берём |
|---|---|
| Формальная FSM с таблицей переходов | Состояний шесть, переходы описаны в §6.3 текстом и однозначны. `TaskStatus` + запись статуса в `tasks.jsonl` дают ту же надёжность без отдельного слоя |
| «Security Policy Engine» как конвейер из 7 стадий | Это одна функция с пятью проверками. Ценность была в **структуре решения** — она взята (`Decision`). Пакет вокруг неё не меняет поведения |
| Слой `tool → capability → policy` | Паки **и есть** группировка прав в v1. Второй маппинг удваивает конфиг и не даёт нового поведения, пока нет `trade.order`. Границу для него зафиксировали в §5 текстом |
| Registry идемпотентности `executionID → status` | Решение о повторе принимает **модель**, а не рантайм — реестр этого не меняет. Рабочее решение взято: явный `timeout`-статус с «состояние неизвестно, не повторяй» (§4.2) + `client_id` в `journal_add`, где дедуп реально нужен |
| `ContextBudgetManager` с порогами 70/85/95 % | Уже есть `agentSoftBudgetChars`, `compactToolMessages` и `TestPackSchemaBudget`. Пороги в процентах — придуманная точность; централизовать имеет смысл, когда появится второй потребитель бюджета |
| `intent` в JSON диспетчера | Дублирует `packs[]` — это признаёт и само предложение. Лишнее поле, которое модель будет путать с паками |
| `confidence` от диспетчера | Локальная 35B откалибрована плохо: поставит 0.9 почти всему. Ту же отладочную ценность даёт сырой JSON диспетчера в `tasks.jsonl` — бесплатно и честно |
| Интерфейс `Brain` под несколько мозгов | Второго мозга нет и не будет в v1 (24 ГБ). `llmChatTools(cfg.BrainPort, …)` уже достаточный шов. Абстракция под несуществующий второй случай |
| `ArtifactManager` с `Create/Register/Expire/Cleanup` | Конкретный баг (чужие артефакты при pending) закрыт полем `Task.Artifacts`. Жизненный цикл с истечением — когда появится, что истекать |
| `pageID` / `frameID` в сигнатурах browser-тулов | Проблема реальная, но это переделка `browser/`. 90 % пользы даёт проверка смены URL перед `browser.act` (§5) |
| Адаптивный `maxAgentSteps` (3/6/10/12/16) | 12 работает. Менять потолок по типу задачи — когда будет статистика, что 12 мало или много |
| Телеметрия из 20 метрик, TTFT, tokens/sec | Один пользователь, один ПК. `dispatcher_ms` + `total_ms` в `tasks.jsonl` и `prompt_ms` из §3.2 отвечают на «где тормозит». Остальное — стенд ради стенда |
| Session token для Web поверх `sameOriginGuard` | `sameOriginGuard` уже закрывает страницу в браузере — единственный реальный вектор. Остаётся «локальный процесс дёргает 127.0.0.1», но такой процесс и так может запустить powershell напрямую. Прибавка к защите ≈ 0 |

Общий принцип разбора: **берём то, что чинит конкретный сценарий отказа, и отклоняем то, что добавляет слой ради будущей гибкости.** У проекта один пользователь, один ПК, одна активная задача и один мозг — инфраструктура, которая окупается на нескольких агентах и нескольких пользователях, здесь окупается отрицательно.

Позиция по «сделать ещё один архитектурный проход перед реализацией»: **не согласен.** Четыре круга ревью уже дали свой результат — крупные дыры (гейт, отмена, pending, протокол `tool_call_id`) закрыты. Главный риск проекта сейчас не отсутствующая абстракция, а пятый круг правок вместо кода. Шаги §12 п. 0–3 дают работающий фундамент; остальное уточняется на живом коде.

### Что уточнилось на живом коде

1. **`deny` был бы недостижим.** По §6.0 `deny` — «в этом режиме нельзя», но все пути вели в `ask` или `hard_block`. Правило, которое его порождает: **подтверждение требует того, кто вправе его дать.** Запрос не от владельца (чат вне allowlist, не-loopback) на опасное действие → `deny`, и рубильник `full` чужому чату прав не добавляет.
2. **Приёмка №23 против §4.2.** Таблица §4.2 даёт отпечатку порог 2 («ты это уже пробовал»), а приёмка требует выхода после **второго** запрещённого вызова. Разведено по смыслу: отказ внутри задачи не передумает → повтор того же запрещённого отпечатка = выход; повторный **сбой** (сеть, кривой аргумент) — прежний порог 4 по тулу.
3. **`chartSystemPrompt` не удалён, а перенесён.** Торговый фильтр с шаблоном WAIT/LONG/SHORT переехал из системного промпта зрения в текст задачи `/chart` (`chartVerdictRules`): дисциплина «лучше честный WAIT» осталась, а цены теперь приходят из `analyze_ticker`, не со скриншота.
4. **`/stop` не был мгновенным даже с протащенным `ctx`.** Сквозной тест против поддельного llama-server показал: после отмены цикл всё равно делал итоговый вызов модели («подведи итог»), то есть пользователь ждал ещё одну генерацию после «остановлено». Починено двумя правками — проверка прерывания стоит **до** итогового прохода, и сам HTTP-запрос к llama-server теперь идёт под контекстом задачи (`llmChatTools(ctx, …)`), так что `/stop` рвёт и генерацию на середине, а не только паузу между шагами.
5. **`prompt_ms` §3.2 добавлен.** `llmChatTools` разбирает блок `timings` из ответа llama-server; `prompt_ms` и `prompt_n` **первого хода исполнителя** (не диспетчера — §3.2 про другое) пишутся в `tasks.jsonl` как `first_prompt_ms` / `first_prompt_tokens`.
6. **Бюджет схем пришлось выгрызать.** Первая сборка паков дала 14 804 символа при пороге 12 000. Порог не двигали (§5): срезаны описания схем, а пустое описание параметра больше не попадает в JSON (кириллица — 2 байта на символ, описания и были основной массой). Итог — 11 610.

### Что проверяется поддельным llama-server

`agent_e2e_test.go` гоняет весь путь (диспетчер → паки → ворота → ответ) против сервера-заглушки на 127.0.0.1. Главное в нём — не сценарии, а то, что **заглушка валидирует исходящие запросы** тем же правилом, которым llama.cpp отвечает 400: у каждого `tool_call` должен быть `tool`-ответ до следующего запроса. Проверено, что сам валидатор ловит нарушение (`TestToolProtocolCheckerDetectsGaps`) — иначе он бесполезен.

Покрыто: полный happy path и состав выданных схем; `first_prompt_ms` в журнале; пауза на подтверждении и возобновление без переигрывания; расширение схем после `request_pack`; выход по `hard_block` без лишнего похода в модель; сломанный JSON диспетчера → fallback в `web`; `/stop` посреди хода исполнителя.

Это не код, а измерения — их нельзя сделать без моделей, Chrome и токена:

## 17. Второй круг живых правок: «у меня отключены инструменты»

Пользовательский диалог после первого прогона вскрыл дефект хуже всех предыдущих: на вопрос «какие у тебя есть инструменты» агент **пересказал свою внутреннюю конфигурацию** («подключен только chat, остальные не подключены»), а на конкретную задачу ответил «у меня отключены инструменты для работы с интернетом… это требует явного разрешения на переключение режима» — и предложил пользователю самому написать Python-скрипт. При этом `request_pack` лежал прямо в схемах и никакого разрешения не требует.

### Причина — в моём же промпте

Строка `Активные наборы инструментов: chat. Нужен ещё один — вызови request_pack` читается моделью как **список прав**, а не как «загружено сейчас». Дальше она честно доложила пользователю, чего ей «не выдали».

Заменено на блок «ТВОИ РУКИ» (`armouryNote`): перечислен весь арсенал, сказано, что любой пак подключается одним вызовом **без разрешения пользователя**, и явно запрещены формулировки «отключены / недоступны / нет доступа / изолированный режим». Отдельно: «спрашивают, что умеешь — перечисли весь список, а не загруженные схемы».

### Разбор вызовов из текста (по вашему решению)

`prose_calls.go`: вызов, написанный прозой, парсится и исполняется **через те же ворота**. Восстановление меняет только то, как намерение пришло, но не то, что разрешено — `guardToolCall` отрабатывает как для обычного вызова (тест `TestRecoveredCallGoesThroughGate`: восстановленный `diskpart` упирается в `hard_block`).

Строгость в обе стороны: пропущенный вызов теряет ход, ложный — исполняет то, что модель лишь упомянула. Поэтому имя должно быть **активным** инструментом, скобки — сбалансированными, а внутри должны быть настоящие аргументы. Отклоняются: упоминание без скобок, `run_command()` без обязательных аргументов, `command=…` из документации, чужие имена (`my_run_command`), позиционные аргументы, разрыв абзацем. Windows-пути разбираются с учётом экранирования: `"D:\tmp\x"` → `D:\tmp\x`, а забытое экранирование `"D:\tmp\x"` не превращается в таб. Счётчик `prose_calls` пишется в `tasks.jsonl` — если доля растёт, проблема в модели или шаблоне, а не в агенте.

| Что | Исправление |
|---|---|
| Моя служебная записка «Инструмент `read_url` не работает… Дальше без него» уходила **пользователю как ответ** — и обещала продолжение, которого не было | мёртвый инструмент прекращает **цикл**, а не ответ: записка идёт модели, итог подводит summary-проход по собранному |

## 18. Третий круг: голос в вебе шёл мимо агента

Пользователь в веб-панели говорил голосом «у тебя же есть консоль, сделай сам» и получал «я работаю в изолированной среде, у меня нет доступа к терминалу». Рубильник рук стоял в `full` и не помогал.

### Причина

Опознавательный знак был в самом ответе: строка `⚡ 60.2 ток/с · промпт 106.1 ток/с`. Её печатает **только потоковый чат** (`llmChatStream`) — слойный агент такую не выдаёт.

В `handleAPIChat` текст уходил в агента, картинки я провёл через vision → диспетчер, а `multipart` с **аудио** проваливался в `buildAttachmentMessages` → `llmChatStream`, где инструментов нет физически. Модель не капризничала: в том пути у неё действительно не было рук, и она это честно сообщала. Никакой рубильник туда не достаёт.

Это нарушение паритета каналов (`AGENTS.md`) и §7 («текст и голос равноправны»): в Telegram голос я через агента провёл, в вебе — забыл.

### Исправление

Вся маршрутизация веб-сообщения вынесена в `routeWebMessage(msg, transcript)` — единственный вход для любого текста, набранного или сказанного. Голос: STT → расшифровка → **тот же** путь (подтверждения «да/нет» голосом, слэш-команды, агент). Транскрипт отдаётся в UI как `transcript`, паритет с телеграмным «🎙 Распознал». Регрессионный тест — `TestWebVoiceAndTextShareOneRoute`.

### Два дефекта, вскрывшихся сразу после починки

| Что | Исправление |
|---|---|
| Модель оборачивала каждую команду в `powershell -Command "…"` **внутри** `run_command`, который и так PowerShell. Двойное экранирование, кракозябры в кириллице, попытки писать временные `.ps1` — 12 шагов на одну команду | правило в паке `console`: обёртки не нужны, писать команду напрямую, временные скрипты ради одной строки не создавать. Стало 1–2 шага |
| В примере правила я сам подсунул `slmgr /xpr` — а он открывает **GUI-окно** и висит до нажатия OK, съедая таймаут | пример заменён на `Get-CimInstance SoftwareLicensingProduct`; добавлен запрет на интерактивные команды (`slmgr` без `/dlv`, `msg`, `notepad`, `pause`, `Read-Host`, мастера установки) |

### Проверено

«проверь, активирована ли Windows» → `console` → **одна** команда `Get-CimInstance SoftwareLicensingProduct | …` → 2 шага, 39 с, `status=done`.

**Отдельно про трактовку:** модель вывела `LicenseStatus: 5` и назвала это «активирована». На самом деле `5 = Notification` (активирована — `1`), и именно это состояние показывает водяной знак. Числа из системы взяты верно, интерпретация выдумана. Инвариант «LLM не выдумывает числа» держится, а вот «LLM не выдумывает смысл чисел» — отдельная задача: где у нас есть детерминированный слой (`trading/`), там трактовку считает код; для системных статусов такого слоя нет.

## 19. Четвёртый круг: рабочий стол, длина рук, меню и сжатие контекста

Пользователь: «ограничений у него не должно быть никаких, доступ везде, безусловно. Но с ограничением: короткие руки, длинные руки». Плюс три отдельных претензии — нет кнопки с командами в Telegram, в веб-панели скорость генерации стоит на месте и не видно контекста, нет `/compact`.

Отправная точка — два ответа с живого прогона. На «сделай скриншот рабочего стола» агент открыл вкладку Chrome и объяснил, что рабочий стол ему недоступен. На «перечисли, чего ты не умеешь» выдал реферат из шести разделов: не вижу экран, не могу делать скриншоты рабочего стола, не могу управлять мышью и клавиатурой вне браузера, не могу запускать произвольные приложения.

### Причина

Модель не капризничала — **всё это было правдой**. Ни одного инструмента за пределами браузера у неё не было: `capture_screenshot` снимает вкладку Chrome, `run_command` не умеет ни окон, ни ввода. Рубильник рук управляет воротами, а ворота не создают рук, которых нет.

Вторая половина причины — в промпте. `armouryNote` не зависел от режима, и блок про файлы в ЛЮБОМ режиме заканчивался строкой «Пиши файлы ТОЛЬКО в рабочие каталоги». При развязанных руках это неправда, и модель честно пересказывала пользователю своё же ограничение. Рубильник переключал ворота, но не то, что модель о себе думает.

### Пак `system` (§5)

Десять инструментов, всё через WinAPI из процесса агента, без внешних зависимостей:
`capture_screen` (весь экран / монитор / окно), `list_windows`, `focus_window`, `type_keyboard`,
`press_keys`, `mouse_action`, `list_processes`, `kill_process`, `launch_app`, `clipboard`.

Скриншот приезжает **артефактом**, то есть уходит человеку файлом тем же путём, что и снимки вкладок, — в Telegram картинкой, в вебе ссылкой.

### Длина рук вместо запретов (§6.2, переписано)

Раньше ядерные команды были `hard_block` в обоих режимах — то есть существовали действия, недостижимые вообще ничем. Теперь недостижимых нет:

### Бюджет схем (§5, уточнение)

Десятый пак не влезал в старую формулировку теста «союз ВСЕХ паков ≤ 12 000». Порог не поднят. Изменилось то, что проверяется: союз всех паков сразу **недостижим** (§4.1 разрешает диспетчеру 1–3 пака, а каждая эскалация `request_pack` и так сверяется с бюджетом), зато первичный выбор диспетчера не проверялся ничем. Теперь «не больше трёх» исполняется кодом (`maxInitialPacks`), а тест перебирает ВСЕ тройки. Худшая — `browser.read + browser.act + system` = 9 214 символов, 77 % лимита.

### Меню команд в Telegram (§9)

`setMyCommands` (17 команд) + `setChatMenuButton` = commands: список появляется по кнопке «☰». `/menu` открывает инлайн-панель, которая одновременно **показывает состояние** (какие руки, идёт ли задача, сколько контекста занято) и переключает его. Нажатия обрабатываются ВНЕ очереди чата, там же, где `/stop` и `/hands`: кнопка «Стоп», поставленная в очередь за длинной задачей, останавливала бы уже следующую.

Кнопка «Что я умею» отвечает **захардкоженным** списком из движка. Причина прямая: на тот же вопрос, заданный модели, и был получен реферат о несуществующих ограничениях. Список возможностей — факт о движке, и брать его надо из движка.

### Живые метрики и контекст (§8)

Скорость «стояла статично», потому что цикл инструментов ходит через `llmChatTools` — он не стримит и раньше не трогал `live` вообще, а агентские пути звали `live.finish(GenStats{})` с нулями. Теперь каждый завершённый ход публикует настоящие тайминги llama.cpp; в панели видно номер хода, накопленные токены, скорость последнего хода (подписано «за ход» — цифра обновляется раз в ход, а не раз в токен) и всегда идущее время.

Окно контекста: «занято» — это `prompt_n` последнего запроса, его считает llama.cpp; всего — из `/props` сервера, а не из `settings.ini` (конфиг говорит, что мы ПОПРОСИЛИ, а сервер мог урезать под VRAM). Вес истории чата — отдельное поле и честно названо оценкой.

### `/compact`

Скользящее окно `maxHistory` просто выбрасывало старые реплики — пользователь видел только то, что бот «забыл» начало разговора. `/compact` заменяет выбрасывание на пересказ: старая часть уходит в сводку, последние 4 реплики остаются дословно (именно к ним относятся «сохрани это», «прочитай подробнее»). Автосжатие срабатывает само на пороге и говорит об этом — молчаливое изменение памяти пользователь бы не заметил. Реплики, пришедшие ПОКА шла сводка, не теряются.

## 20. Пятый круг: агент нажимает кнопки сам

Пользователь: «У киборга же есть руки, кликанье мышкой, глаза. Пусть откроет телеграм, найдёт свой чат и потыкает кнопки».

Половина предпосылки была неверна: рук и глаз хватало не везде. Проверка вскрыла восемь дефектов, семь из них — в нашем коде.

### Глаз на рабочем столе не было

`capture_screen` отдавал МОДЕЛИ путь к файлу, а пиксели уходили человеку. Мышь умеет кликать только по координатам — то есть агент мог нажать куда угодно и не мог узнать, куда надо.

Появился параметр `look=`: снимок ужимается до 1200 px, уходит в то же зрение, которым разбираются присланные картинки, и возвращается ТЕКСТОМ — описание экрана плюс координаты найденного элемента. Пересчёт нормированной сетки 0..1000 в пиксели экрана делает Go, а не модель: у снимка окна начало координат не в нуле, а у монитора слева от основного X вообще отрицательный.

Архитектурно иначе и нельзя: §7 запрещает смешивать `image_url` со схемами инструментов в одном запросе к llama-server, поэтому зрение работает отдельным вызовом без инструментов.

Точность измерена, а не предположена: перекрестья в найденных точках легли на строку чата Kibborg и на поле поиска, расхождение с контрольным замером — 15 пикселей.

### Что чинилось по дороге

| Дефект | Как проявлялся | Исправление |
|---|---|---|
| **Первый `chromedp.Run` шёл на дочернем контексте с таймаутом** | «Chrome умирает, стоит агенту подключиться». `RemoteAllocator.Allocate` вешает уборку на ТОТ контекст, где произошла аллокация; мы отменяли его тем же `defer` в конце `attach`, и уборка через мгновение закрывала вкладку, к которой только что подключились. Единственная вкладка — Chrome выходил целиком | первый `Run` идёт на самом `pageCtx`; ограничение по времени вынесено наружу в `select`, а выход — через `detachPage`, который сначала снимает `Target` |
| **Синтетический `el.click()` не работает на Telegram Web** | клик «выполнен», чат не открылся: приложение слушает pointerdown/mousedown | поиск элемента по надписи делает JS, а нажатие — настоящее `Input.dispatchMouseEvent` по координатам центра |
| **Кликать было нечем, кроме селектора** | `get_html` на большом SPA обрезается и упирается в таймаут, модель начинает угадывать селекторы, `chromedp.Click` ждёт несуществующий узел все 45 с. Шесть попыток подряд — восемь минут в никуда | `click_element` принимает `text=` — надпись, как её видит человек. Точное совпадение приоритетнее вхождения |
| **Перехват сети включался при каждом подключении** | лишняя инструментовка на живом приложении с постоянным потоком | домен Network поднимается лениво, только когда его спросили, и честно сообщает, что запись началась с этого момента |

Отдельно — среда, а не код: на порту 9222 одновременно оказались два браузера (пользовательский на IPv4 и тестовый на IPv6). Движок брал список вкладок из одного, а подключался к другому. Час диагностики ушёл именно на это, и вывод для будущего простой: **прежде чем чинить код, посмотри, кто вообще слушает порт.**

### Проверено вживую

Полная цепочка, без участия человека в середине:

1. агент подключился к Chrome по CDP, прочитал текст Telegram Web — вкладка выжила;
2. `click_element text=Kibborg` настоящим событием мыши — чат бота открылся (`web.telegram.org/k/#@Kibborg_Davinchi_bot`);
3. `click_element text=Статус` — бот ответил в чат: «🩺 Состояние · Мозг: готов, порт 8083 · Контекст 4175/32768 (12%) · Последняя генерация 61.1 ток/с»;
4. `click_element text=Короткие руки` — журнал движка: `[HANDS] режим переключён на safe (telegram-menu:591591074)`.

Последний пункт — объективное доказательство: нажатие в браузере дошло до серверов Telegram, вернулось в бота callback-запросом, обработчик отработал и переключил состояние.

Нажатия того же меню самим пользователем подтверждены журналом раньше: 12:10:31 руки→длинные, 12:10:35 руки→короткие, 12:10:45 сжатие 12→6 реплик (5402→2167 токенов).

### Чего агент по-прежнему не умеет

Вести многошаговую работу в тяжёлом SPA без подсказок. Оставленный сам по себе он вбивает имя чата в поиск, теряет открытый чат, прокручивает ленту вверх от нужной кнопки. Каждый ОТДЕЛЬНЫЙ шаг («нажми кнопку с надписью X») выполняется надёжно; цепочка из четырёх шагов разваливается примерно в половине случаев. Это ограничение модели, а не инструментов, и честнее записать его сюда, чем выдать половину прогонов за успех.

## 21. Слой видео: ffmpeg как нож, а не как модель

Пользователь: «дать киборгу ffmpeg, чтобы можно было дать ему видео на анализ, вытащить с него текст и по этому тексту искать — например, проект на GitHub».

Ключевое решение принято сразу и определило всё остальное: **видео — это контейнер, а не модальность.** Никакой «модели для видео» в движке нет и не будет. ffmpeg режет ролик на то, что движок УЖЕ умеет глотать:

```
дорожка речи → voice.go  → TypeWhisper/whisper.cpp → текст
кадры        → images.go → зрение (mmproj)          → текст
метаданные   → ffprobe                              → текст
```

Из этого следует всё дальнейшее. В частности — ответ на «любые объёмы»: длина ролика упирается в диск, а не в окно контекста.

### Как устроены «любые объёмы»

Одно декодирование в 16 кГц моно WAV, затем нарезка сегментным мультиплексором по 5 минут. Метки времени точны по построению — у PCM постоянный битрейт, поэтому начало куска считается арифметикой, а не гаданием. Исходник декодируется ровно один раз независимо от длины.

В контекст модели уходит ВЫЖИМКА, полная расшифровка ложится файлом рядом. Длинный текст сворачивается картой-свёрткой: куски по 6000 символов пересказываются по отдельности, пересказы склеиваются, и раунд повторяется, пока не влезет. Измерено на живой модели: 22 800 → 584 символа за 17 секунд.

Приоритет источников текста: субтитры хостинга → субтитры внутри контейнера → распознавание. Первые два бесплатны и точнее распознавания. Для ссылки, когда кадры не нужны, качается только звук: у часового доклада это разница между 30 мегабайтами и гигабайтом.

Кадры считаются по правилу, а не «сколько попросили»: речи нет вовсе (немой скринкаст) — шесть кадров, они единственный источник; речь есть и ролик длинный — ноль, кадры почти ничего не добавят к расшифровке; короткий ролик с речью — три. Каждый кадр стоит отдельного запроса к зрению, и платить им за пустоту незачем.

### Два дефекта, которые поймал тест, а не живой ролик

`chunkText` — резка текста на куски перед свёрткой. Оба дефекта в ней стоили бы дорого.

**Первый: вечный цикл.** Когда до конца куска оставался один символ, отступ до ближайшего пробела обнулял длину — ни один символ не уходил из остатка, цикл крутился бесконечно. Движок вставал бы намертво на пересказе длинной расшифровки, то есть ровно на той задаче, ради которой всё делалось.

**Второй: слова, порванные пополам.** При малом остатке места кусок добирался по одному символу, и на стыке кусков слово разрывалось. Пересказ такого стыка портится, а поиск по расшифровке перестаёт находить слово.

Правило, которое из этого выросло: **если в остаток не влезает целое слово — закрывай кусок, а не добирай по символу.**

Оба дефекта нашлись потому, что тест проверял не «работает ли», а конкретные утверждения: ни один кусок не длиннее лимита, сумма слов равна исходной, ни один кусок не обрывается посреди слова.

### Артефакты кладутся не там, где удобно, а там, где их отдадут

`runtime/browser/media`, а не `runtime/media`. Причина не в красоте: `/api/files` отдаёт веб-панели ТОЛЬКО корень `runtime/browser`, и расшифровка, сохранённая мимо него, оказалась бы файлом без ссылки. Пак `system` наступал на это раньше и решил так же (`runtime/browser/desktop`) — второй раз наступать не стали.

### Приём ролика: та же труба, что у картинки

Ролик, присланный в чат, разбирается ДО диспетчера и превращается в текст — ровно как картинка по §4. Поэтому «разбери видео и найди проект на гитхабе» работает само собой: к моменту выбора инструментов задача уже текстовая, и дальше это обычная работа паков `web` и `browser`.

Telegram отдаёт ботам только 20 МБ — это ограничение их API, обойти его нечем. Ответ на него — не отказ, а два рабочих пути: прислать ссылку либо назвать путь к файлу на диске, где размер не важен вовсе. Это прямое следствие правила «ограничений нет, есть длина рук»: там, где стена настоящая, называются двери.

### Проверено вживую

Проверка сделана на СИНТЕЗИРОВАННОМ ролике: SAPI наговаривает русский текст про торговую стратегию, слайд с адресом репозитория рисуется через System.Drawing, ffmpeg собирает это в mp4. Ловушки «проверил на своём файле, которого нет у других» так не возникает — `video_live_test.go` запускается только при `KIBBORG_LIVE_MEDIA=путь` и в обычном прогоне пропускается.

Цепочка целиком, через `/api/chat` веб-панели, без единого ручного шага в середине:

1. загрузка ролика → статусы «распознаю речь», «смотрю 3 кадра»;
2. речь распознана: «В этом ролике разбирается торговая стратегия… риск на одну сделку ограничен двумя процентами депозита»;
3. зрение прочитало со слайда дословно: `github.com/freqtrade/freqtrade`, `stoploss = -0.02`, `timeframe = '1h'`;
4. диспетчер выдал план «найти репозиторий freqtrade на GitHub → прочитать описание → рассказать»;
5. агент нашёл проект и ответил, сославшись И на речь, И на значения со слайда.

Отдельно ценный результат: распознавание услышало «Rectrade» вместо «Freqtrade» — синтезированное произношение сбило его. Проект всё равно найден, потому что зрение прочитало точное имя со слайда. Это и есть довод в пользу двух каналов сразу: они ошибаются по-разному.

### Чего слой не делает

Не понимает происходящее в динамике. Кадры берутся точками, поэтому «в какой момент он нажал кнопку» или «что изменилось между 3:10 и 3:20» слой не отвечает — он видит несколько неподвижных картинок и слышит речь. Для туториалов, докладов и разборов стратегий этого достаточно; для разбора движения — нет, и обещать обратное не стоит.

## 22. Слой 0: указание без предмета

Живой случай, найденный при проверке разбора видео. Первым сообщением в пустом чате:

> Найди мне этот проект на гитхабе

Опоры для слова «этот» в разговоре не было — предыдущих реплик ноль. Агент не спросил «какой?», а выдал подборку заметных open-source проектов 2026 года: OpenClaw, Ollama и прочие, со ссылкой на источник. Шесть шагов, сорок секунд поиска, аккуратно оформленный ответ **на другой вопрос**.

Это не галлюцинация в обычном смысле — источник он привёл, факты в нём настоящие. Это подмена вопроса, и она опаснее выдумки: выдумку видно, а правдоподобная подборка выглядит как работа.

### Где ставится проверка

Перед диспетчером, отдельным слоем 0. Причина простая: «найди этот проект» в пустом чате не станет понятнее ни от выбора паков, ни от шести шагов поиска. Дешевле всего отказаться от работы ДО того, как она началась.

Проверка детерминированная, в Go, без обращения к модели. Это тот же приём, что и §7 с тикером со скриншота: «не определился — спроси», решение принимает код, а не уговоры в промпте.

### Правило намеренно молчаливое

Ложное срабатывание здесь дороже пропуска. Агент, который переспрашивает вместо работы, — ровно то поведение, которое из этого движка выкорчёвывали главой про длину рук. Поэтому вопрос задаётся, только когда доказано, что опоры нет НИГДЕ:

- **в самом сообщении** — нет ссылки, пути к файлу, кавычек, латинского имени и нет разбора вложения (видео или картинка уже превращены в текст, §21 и §4);
- **в разговоре** — окно диалога пусто И сумка найденных ссылок пуста;
- **и предмет не самоочевиден** — «этот компьютер», «этот бот», «этот экран», «этот чат» указывают на то, что и так вокруг. Спрашивать «какой компьютер?» — глупость, которая дискредитировала бы правило целиком.

Сравнение с самоочевидными предметами идёт **по основе**, а не по слову: «этого экрана», «на этом компьютере» — те же предметы в других падежах, а словарь всех форм разросся бы до бесполезности. Основа заведомо ловит лишнее («эту компанию» подпадает под «комп») — и это правильная сторона ошибки: лишнее совпадение означает МОЛЧАНИЕ, то есть прежнее поведение, а пропуск означает глупый вопрос.

Обязательное условие — намерение: поручение («найди», «скачай») или вопрос («что это за…»). Без него «это интересно» и «вот это да» превращались бы в допрос на ровном месте.

### Вопрос не должен звучать как отказ

Формулировка цитирует слова пользователя (его собственная фраза всегда грамматична, в отличие от попытки просклонять существительное за него) и называет три способа дать опору:

```
🤔 Уточни: «этот проект» — это про что?

В этом чате об этом ещё не было речи, а угадывать не буду — подсуну не то.
Дай опору, дальше сделаю сам:
• ссылку;
• точное название;
• видео, скриншот или файл, где это упоминается — разберу и найду по нему.
```

Тест это проверяет прямо: в вопросе обязаны быть слова про ссылку и название и обязаны отсутствовать «не могу», «недоступно», «ограничен».

### Вторая половина — в промпте

Детерминированная проверка закрывает только доказуемый случай. Когда история в чате ЕСТЬ, но нужного предмета в ней нет, доказать это кодом нельзя — там судит модель. `referentRule` в промпте исполнителя сформулирован двусторонне намеренно: «не понял — спроси один раз» И «понял — работай молча, без вопросов». Односторонняя формулировка сделала бы из агента переспрашивателя.

### Проверено

Тест написан несимметрично: случаев «молчи» втрое больше, чем «спроси» — пропуск дёшев, лишний вопрос дорог.

Живьём, на работающем движке:

1. пустой чат, «Найди мне этот проект на гитхабе» → уточняющий вопрос за **0.0 секунды** вместо шести шагов и сорока секунд;
2. пустой чат, «какие процессы больше всего жрут память на этом компьютере» → правило промолчало (предмет самоочевиден), задача ушла в пак `system` и вернула реальный топ процессов за 13 с.

Первый прогон доказывает, что правило срабатывает. Второй — что оно не мешает работать, а это здесь важнее.
